Run 26-30B MoE models in about 3 GB of RAM

A Rust runtime that streams Mixture-of-Experts weights from NVMe instead of holding them hostage in memory. CPU only, no GPU, on an ordinary Linux x86_64 machine.

Install the runtime

curl -sSL https://y0sif.github.io/ramvamp/install.sh | bash

Linux x86_64 only. Puts ramvamp and ramvamp-repack in /usr/local/bin. Re-run it later to upgrade. On any other platform it refuses and installs nothing, because io_uring is a Linux interface and the fast kernels are AVX2 plus F16C.

Then install a model

ramvamp-repack install --output ~/models/qwen3-30b-a3b.rvmp

This is a 17.35 GiB download, so the installer will not start it for you. It streams the source GGUF straight into the packed layout, so it needs 17.35 GiB free and not twice that. Put the path on an NVMe SSD.

Then run it

ramvamp chat --model ~/models/qwen3-30b-a3b.rvmp --tui

Or ramvamp serve for an OpenAI-compatible endpoint on loopback, with streaming SSE and tool calls.

Also available as a prebuilt tarball / from source

Measured, not projected

Qwen3-30B-A3B Q4_K_M, cold page cache, inside a memory.max=3G cgroup with memory.swap.max=0, on the reference machine: Intel Core Ultra 9 185H, CPU only, Micron 2400 DRAM-less QLC NVMe.

Decode about 2 tok/s 1.46 to 2.19 across context 64 to 3,961, on this DRAM-less QLC drive
Prefill 11.25 tok/s at context 512
Peak RAM 2,497 to 2,929 MiB of a 3,072 MiB ceiling
Model on disk 17.35 GiB about a 6x memory saving over loading it
Fidelity 1.04e-2 mean KL full-vocab, against llama.cpp on identical weights, top-1 agreement 8/8

Two tokens per second is the honest headline, and it is I/O-bound: decode reads up to about 1.1 GB of expert weights per token, so the number belongs to the drive as much as to the code. No figure is published here without naming the drive it came from. Full table and conditions: docs/benchmarks.md.

How it works

Experts live on disk

In a fine-grained MoE model the routed experts are most of the weights, and a token needs 8 of the 128 in each layer. They stay in a page-aligned packed format on NVMe and are fetched only when the router asks.

Explicit reads, never mmap

Expert reads go through io_uring with O_DIRECT, batched per layer. That bypasses the page cache, so expert traffic costs the memory budget nothing. Demand paging is the alternative, and TurboFieldfare measured mmap 3.54x slower per cold expert read.

Common weights are mmap'd

Embeddings, attention, routers, norms and the lm_head are about 1,023 MiB, touched on every token, and the page cache keeps them resident.

A small LFU cache

Eleven slots per layer out of 128 experts at the default budget, absorbing 53 to 59 percent of requests. Hits dispatch immediately and hide the latency of the misses behind compute.

Install repacks, it does not convert

The GGUF is streamed into the packed layout in one pass. Quantized bytes are copied unchanged, nothing is requantized, and no shard is ever materialized in heap memory.

CPU-first kernels

AVX2 and FMA, with F16C for attention, detected at runtime, on a pinned compute pool that respects CPU topology. There is a scalar fallback, and it is slower.

An OpenAI-compatible server

ramvamp serve speaks /v1/chat/completions on loopback with streaming SSE, tool calls, and KV prefix reuse across requests. It rejects fields it cannot honour exactly rather than accepting them quietly.

A context dial you can price

ramvamp plan costs a configuration before loading anything, and refuses an impossible one. Named profiles make a 32K setup a thing you can write down instead of rediscover.

FAQ

How does a 30B model fit in 3 GB of RAM?

It does not fit, and it is never asked to. Only 8 of 128 experts per layer are needed for a given token, so the common weights stay memory-mapped at about 1,023 MiB and the experts stay on disk, read on demand through a small per-layer cache. Measured peak resident memory is 2,497 to 2,929 MiB inside a 3,072 MiB ceiling.

How fast is it, honestly?

About 2 tokens per second of decode on the reference machine, 1.46 to 2.19 across context 64 to 3,961, on a Micron 2400 DRAM-less QLC NVMe. Prefill is 11.25 tok/s at context 512. That is the number, and a faster drive is the thing most likely to move it.

Do I need a GPU?

No. ramvamp is CPU-first and there is no GPU path. The kernels are AVX2 plus FMA, with F16C for attention, detected at runtime.

Do I need an NVMe SSD?

For these numbers, yes. Decode reads up to about 1.1 GB of expert weights per token, so the drive is the throughput. It will run on SATA or a spinning disk and be far slower than anything documented here.

What do I actually have to download?

The runtime is a 6 MB tarball. The model is separate and is a 17.35 GiB download, streamed straight into the packed layout so it needs 17.35 GiB free rather than twice that. The installer prints the command and stops; starting a 17 GiB fetch is your decision, not a script's.

Why Linux x86_64 only?

io_uring is a Linux kernel interface and the expert streamer is built on it. The fast kernels are AVX2 plus F16C, which is x86_64. Everywhere else the code compiles and runs on fallback paths that no published figure describes, so the installer refuses rather than implying otherwise. Cross-platform builds wait for an I/O path worth measuring there.

Is it finished?

No. This is v0, and it runs: coherent generation on CPU inside a 3 GB cgroup with a cold page cache, validated against llama.cpp on identical weights. The plan of record, including what is not done, is docs/roadmap.md.
